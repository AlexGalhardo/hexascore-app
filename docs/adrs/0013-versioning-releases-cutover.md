# ADR 0013: Versioning from v0.1.0, vukem-style releases, big-bang cutover

Status: accepted (2026-10-28). Decisions: brainstorming D-20, D-21; owner requirements 7 (releases follow `github.com/AlexGalhardo/vukem/releases`) and Git rules (branch `legacy`, no history rewrite).

## Context

The legacy app is at 0.0.25 with release-please. vukem releases are tagged `vX.Y.Z`, one per task group, with a changelog generated by git-cliff from Conventional Commits, a GitHub release, and rules: never edit released changelog sections, never move a pushed tag, push tags one at a time (`vukem/.claude/rules/changelog.md`, `vukem/docs/tooling.md [SITE PAGE MISSING]`). Branch `legacy` was created from `main` at `97243cb` and pushed on 2026-10-28.

## Decision

- **Versioning**: `hexascore-vukem` starts at `v0.1.0`; each roadmap task group that ships to staging is a `v0.N.0` release; patch releases for fixes; **`v1.0.0` = parity with the legacy app and successful cutover**. SemVer applies to the public API separately (`API_VERSION`, `/api/v1` path), so app releases do not imply API breaks.
- **Release mechanics**: same as vukem: Conventional Commits validated by a commit lint, changelog generated (git-cliff config copied and adapted), tag pushed one at a time, GitHub release with notes, `CHANGELOG.md` in Keep a Changelog format with an `[Unreleased]` section that is never edited by hand after release.
- **Git**: `hexascore-vukem/` is initialised as its own repository and pushed to `github.com/AlexGalhardo/hexascore-app` as `main` (replacing the Next.js tree there); branch `legacy` is immutable; no force-push or history rewrite without an explicit owner request; feature branches merge through PRs to `main` with required checks.
- **Cutover**: big-bang after parity. Staging on Railway with a production data copy; gates green (Playwright + axe, k6, Schemathesis, ZAP, parity checklist, Lighthouse budgets); a short read-only window on the legacy app; final data migration; DNS switch; the legacy deployment on Vercel stays alive for 30 days for rollback with a documented DNS revert and a data reconciliation plan for writes made after cutover.

## Alternatives considered

- **Continue from 0.0.26.** Mixes two products in one sequence. Rejected.
- **Route-by-route strangler.** Two auth systems and databases during months of transition. Rejected.
- **Traffic canary.** Needs full parity and a shared database before starting; gains little over big-bang. Rejected.

## Consequences

- Positive: clear meaning for 1.0; release discipline identical to the framework; a single risky moment (cutover) with a rehearsed rollback.
- Negative: no production feedback until cutover (mitigated by staging with real data and a private beta of the new site on a subdomain if the owner wants it).
- Obligations: SDD 11 details the pipeline, the migration scripts, the read-only window, the rollback runbook; the roadmap orders work to reach parity first.
