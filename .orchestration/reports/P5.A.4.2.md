# P5.A.4.2 Offline mutation queue

Branch `agent/senior/P5.A.4.2` @ 825389f, stacked on `agent/senior/P5.A.4.1` @ 7844559 (merge order: FIX-mobile-root-wiring -> P5.A.4.1 -> this).

## What changed

- `src/queue/store.ts`: `createMutationStore(storage, newKey, now)` over the `KeyValueStorage` port from `src/query/persister.ts` (one row `hexascore.mutationQueue` = `{userId, entries}`). Entries are exactly `{id, op, itemId, payload, idempotencyKey, createdAt, attempts}`. `op` is `rating | status | timeToBeat | list:<listId>` (single list add/remove), `payload` is `{method: "put", body} | {method: "delete"}`, so a put and a delete on the same resource replace each other. A newer write for the same `(itemId, op)` removes the queued one and gets a fresh key. Over 50 entries `enqueue` returns `null`, so the caller can show a toast. Nothing is dropped silently. If another user enqueues, the previous user's entries are discarded. An unparsable row starts empty.
- `src/queue/policy.ts`: `decide(outcome, entry, now)` is the SDD 10 §7.3 table:
  - 2xx: `applied` with the server body.
  - 409 without a domain code (vukem's in-flight key): `retry`.
  - 409 `rating-not-released` / `status-not-completed`, 422, any other 4xx: `rollback` with `code` and `retryAfter`.
  - 429 `item-ratings-limited`: `rollback` with `Retry-After`.
  - 404: `drop`, no toast.
  - 5xx: on the 5th attempt, or when the entry is older than 72 h, `drop` with a toast.
  - Network failure (status 0): retry until 72 h.
  - 426: `pause`.
  - 401: `halt`.
  - Backoff `[2 s, 10 s, 60 s]`.
- `src/queue/drain.ts`:
  - `createDrain`: FIFO, one run at a time. It does nothing when offline, when `paused()` is true (wire `appClient.upgradeRequired()`) or when no user is known. A different user clears the queue. Entries older than 72 h are dropped before they are sent. A retry stores `attempts + 1` and schedules the next drain at the backoff. Entries are removed by id, so a write replaced while in flight survives the old result. `onResult(entry, result)` hands `applied | rollback | drop` to the UI for the cache replace and the toast.
  - `startQueue(drain, {subscribeNetwork, subscribeAppActive})` drains at start, on `online` and on foreground.
  - `sendEntry(appClient, entry)` maps each op to `ratingsPut/Delete`, `statusPut/Delete`, `timeToBeatPut/Delete` and `listsItemsPut/Delete` with the entry's stored key.
- `src/api/client.ts`: `write` now records `Retry-After` and attaches it to the thrown `ApiError` as `retryAfter`. `ApiError` keeps no headers, and the 429 rollback needs the value. `instanceof ApiError` still holds for existing callers.

No new dependencies.

SDD: 10 §5 (mutation queue row), §7.3, §8 (token expired: replay only for the same user; 426 with a pending queue: paused), FR-10-4. Idempotency: <https://vukem.dev/docs/rest-apis/idempotency> (409 in flight, 422 reused key). The in-flight 409 has no `code`, which I confirmed in vukem `api/idempotency.go` (`errs.New(http.StatusConflict, ...)`).

## Limits

- The queue is not instantiated in `src/auth/runtime.ts` yet. The session has no user id: the only identity source is `GET /me`, which the app does not read before P5.B. The first enqueue site, the rate sheet P5.B.2.3, wires it there: `createMutationStore(cacheStorage, appClient.newIdempotencyKey)`, `createDrain({send: (e) => sendEntry(appClient, e), paused: () => appClient.upgradeRequired(), online: () => getNetworkState() !== "offline", currentUser: <me id>})`, `startQueue(drain, {subscribeNetwork, subscribeAppActive})`. P5.B.2.3 also owns the optimistic cache update and the toasts.
- The queue is deliberately left out of `wipeUserData`. 401 also runs that wipe, and SDD 10 §8 says the queue replays for the same user after re-login. A different user discards it through the user binding. If the specialist wants logout or ban to clear it explicitly, that is a one-line `store.clear()` in runtime.
- No device run (owner-gated).
